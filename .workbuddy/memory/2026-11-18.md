## 后端 B1–B3 已落地（commit 待提交）

技术栈 **FastAPI + SQLAlchemy 2.0 + Alembic + psycopg3 + PostgreSQL**，代码在 `backend/`。

**隔离实例**：`initdb` 到 `backend/.pgdata`，端口 **55433**，role/库均 `miyun`（`--auth=trust`），
**不碰本机 5432 上舆情系统的库**。这条路是被环境逼出来的——5432 的 role 名字不可知，且
sandbox 会在命令结束时杀掉 pg_ctl 拉起的进程，所以建库/灌库/自检必须在**同一条命令内闭环**：
`pg_ctl start → isready → alembic → seed → api_checks → pg_ctl stop`。
另：postgres 拒绝以管理员身份直接运行（必须走 pg_ctl 的受限令牌）。

**规模**：34 张表（32 行清单 + dept + import_row）+ 3 视图 + 1 指标快照；种子 1.49 MB 紧凑 JSON。

**实施中修正的三个设计点**
1. 预警指向无明细人员（中 2284 / 低 2646 只有计数）→ 不造 4,930 行假人，`alert.person_id` 可空 + 新增 `alert.person_ref` 留原编号。
2. 部门口径含不含待核实 → `v_dept_stats` 增 `is_unrated`，API 默认 `unrated=false`（=前端 486 口径）。
3. 标签口径必须按人去重：同一人两个标签同属一个部门时 `deptStats()` 只算 1 人 → SQL 用 `count(DISTINCT person_id)`，否则公安分局虚高到 278（真实 246）。

**验收（实跑）**：`alembic upgrade head` 0001_init head；34 表 + 3 视图；
`python -m app.seed --verify` 28 张表行数 + 5 项口径全绿（交叉 50 / 并集 245 / 主责 486 / 标签 667 人次 / 跨部门 168）；
`python -m tools.api_checks` 45 条断言全绿（五大数逐项相等、dept 与 deptTag 不混用、台账 46 条 22↑24↓）。

**踩过的坑**：PG 里 `cross`/`dual` 是关键字（CTE 名要加后缀）；`CREATE OR REPLACE VIEW` 不能改列顺序（改成先 DROP 再 CREATE）；`town` 表没有 `sort` 列（排序用 code）；psql 传中文 SQL 在 GBK 控制台报 invalid byte sequence；SQLAlchemy 无 relationship 的表不保证插入顺序（seed 里逐表 `flush()`）。

**下一步**：B4（写 API + 服务端审计 + 服务端掩码——掩码必须移服务端，否则接真实数据即假脱敏）、B5（前端 `assets/data.js` 换数据源）。S10 仍挂起等领导定名。
