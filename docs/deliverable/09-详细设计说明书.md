### 2.3 核心表 DDL

#### person（人员主档）

```sql
CREATE TABLE person (
    person_id         VARCHAR(32)  PRIMARY KEY,
    id_card_no        VARCHAR(128) NOT NULL,            -- 加密存储
    id_card_hash      VARCHAR(64)  NOT NULL,            -- 用于唯一索引与查询
    name              VARCHAR(50)  NOT NULL,
    name_pinyin       VARCHAR(100),
    name_initials     VARCHAR(20),
    gender            CHAR(1),
    birth_date        DATE,
    nation            VARCHAR(20),
    phone_enc         VARCHAR(128),
    domicile_addr     VARCHAR(200),
    residence_addr    VARCHAR(200),
    street_code       VARCHAR(12)  NOT NULL,
    community         VARCHAR(50),
    grid              VARCHAR(50),
    master_dept       VARCHAR(20)  NOT NULL,
    category_code     VARCHAR(10)  NOT NULL,
    control_level     VARCHAR(20)  NOT NULL,
    control_rank      SMALLINT     NOT NULL,
    dual_reg_flag     BOOLEAN      DEFAULT FALSE,
    dual_reg_type     VARCHAR(20),                      -- GA_WJ / GA_XF / OTHER
    multi_tag_flag    BOOLEAN      DEFAULT FALSE,
    tag_count         SMALLINT     DEFAULT 1,
    key_flag          BOOLEAN      DEFAULT FALSE,
    guardian_name_enc VARCHAR(200),
    guardian_phone_enc VARCHAR(200),
    bao_lian_cadre    VARCHAR(50),
    bao_lian_phone    VARCHAR(20),
    status            VARCHAR(10)  NOT NULL DEFAULT 'ACTIVE',  -- ACTIVE / REDUCED / MOVED
    reduce_reason     VARCHAR(100),
    reduce_date       DATE,
    is_minor          BOOLEAN      DEFAULT FALSE,
    first_reg_date    DATE         NOT NULL,
    last_update_time  TIMESTAMP    NOT NULL DEFAULT now(),
    remark            TEXT,
    CONSTRAINT uk_person_idcard UNIQUE (id_card_hash)
);

CREATE INDEX idx_person_street_rank ON person (street_code, control_rank) WHERE status = 'ACTIVE';
CREATE INDEX idx_person_dept        ON person (master_dept, status);
CREATE INDEX idx_person_category    ON person (category_code, control_rank);
CREATE INDEX idx_person_status      ON person (status);
CREATE INDEX idx_person_name_trgm   ON person USING gin (name gin_trgm_ops);
CREATE INDEX idx_person_initials    ON person (name_initials);
CREATE INDEX idx_person_flags       ON person (dual_reg_flag, multi_tag_flag) WHERE status = 'ACTIVE';
```

> **id_card_hash 的作用**：身份证号加密存储后无法直接建唯一索引和等值查询，因此另存一份 HMAC-SHA256 哈希（加盐、不可逆）用于唯一约束与精确匹配。查询时对入参做同样哈希再匹配。

#### person_tag（人员标签）

```sql
CREATE TABLE person_tag (
    tag_id          BIGSERIAL    PRIMARY KEY,
    person_id       VARCHAR(32)  NOT NULL REFERENCES person(person_id),
    category_code   VARCHAR(10)  NOT NULL,
    level_code      VARCHAR(20)  NOT NULL,
    std_risk_rank   SMALLINT     NOT NULL,
    list_reason     TEXT,
    list_date       DATE         NOT NULL,
    source_dept     VARCHAR(20)  NOT NULL,
    eval_basis      TEXT,
    basis_complete  BOOLEAN      DEFAULT FALSE,
    is_dual_reg     BOOLEAN      DEFAULT FALSE,
    tag_status      VARCHAR(10)  NOT NULL DEFAULT 'VALID',  -- VALID / RELEASED
    approve_status  VARCHAR(10)  DEFAULT 'PASSED',
    created_by      VARCHAR(32),
    created_time    TIMESTAMP    NOT NULL DEFAULT now(),
    updated_time    TIMESTAMP
);

CREATE UNIQUE INDEX uk_tag_person_cat_dept
    ON person_tag (person_id, category_code, source_dept) WHERE tag_status = 'VALID';
CREATE INDEX idx_tag_category_level ON person_tag (category_code, level_code) WHERE tag_status = 'VALID';
CREATE INDEX idx_tag_dept           ON person_tag (source_dept, tag_status);
```

> 唯一索引包含 `source_dept`：同一类别由公安和卫健各报一条时保留两条（双在册的物理表达），再由 `is_dual_reg` 标识。若同一部门重复报送同一类别，则唯一约束拦截，走合并逻辑。

#### risk_change（等级变动）

```sql
CREATE TABLE risk_change (
    change_id       BIGSERIAL    PRIMARY KEY,
    person_id       VARCHAR(32)  NOT NULL,
    tag_id          BIGINT       NOT NULL,
    change_type     VARCHAR(10)  NOT NULL,        -- UP / DOWN
    from_level      VARCHAR(20),
    to_level        VARCHAR(20)  NOT NULL,
    from_rank       SMALLINT,
    to_rank         SMALLINT     NOT NULL,
    reason          TEXT         NOT NULL,
    approval_id     BIGINT,
    applicant       VARCHAR(32)  NOT NULL,
    apply_time      TIMESTAMP    NOT NULL DEFAULT now(),
    approver        VARCHAR(32),
    approve_time    TIMESTAMP,
    effective_time  TIMESTAMP,
    status          VARCHAR(20)  NOT NULL DEFAULT 'PENDING', -- PENDING/APPROVED/REJECTED/EFFECTIVE
    file_no         VARCHAR(50)                          -- 上调备案号
);
CREATE INDEX idx_rc_person ON risk_change (person_id, apply_time DESC);
CREATE INDEX idx_rc_time   ON risk_change (apply_time);
```

> 该表**只允许 INSERT 与状态字段 UPDATE**，通过触发器禁止删除与修改历史字段（见 4.5）。

### 2.4 字典设计

```sql
CREATE TABLE sys_dict (
    dict_code   VARCHAR(30) PRIMARY KEY,   -- category / level / street / dept / reason ...
    dict_name   VARCHAR(50) NOT NULL,
    version     INT DEFAULT 1,
    remark      VARCHAR(200)
);

CREATE TABLE sys_dict_item (
    item_id     BIGSERIAL PRIMARY KEY,
    dict_code   VARCHAR(30) NOT NULL,
    item_code   VARCHAR(30) NOT NULL,
    item_name   VARCHAR(50) NOT NULL,
    parent_code VARCHAR(30),
    sort_no     INT DEFAULT 0,
    ext_json    JSONB,          -- 等级项存 std_risk_rank
    status      CHAR(1) DEFAULT '1',
    CONSTRAINT uk_dict_item UNIQUE (dict_code, item_code)
);
```

**关键字典：等级映射（ext_json 存 rank）**

| dict_code | item_code | item_name | parent_code | ext_json |
|---|---|---|---|---|
| level | HIGH | 高风险 | — | `{"rank":2}` |
| level | MID | 中风险 | — | `{"rank":4}` |
| level | LOW | 低风险 | — | `{"rank":6}` |
| level | EXTREME | 个人极端 | — | `{"rank":1}` |
| level | A | A 类 | — | `{"rank":2}` |
| level | B | B 类 | — | `{"rank":4}` |
| level | C | C 类 | — | `{"rank":6}` |
| level | L1 | 一级 | — | `{"rank":2}` |
| level | L2 | 二级 | — | `{"rank":4}` |
| level | L3 | 三级 | — | `{"rank":6}` |
| level | FOCUS | 关注对象 | — | `{"rank":6}` |
| level | GENERAL | 一般关注 | — | `{"rank":6}` |
| level | UNKNOWN | 风险不详 | — | `{"rank":8}` |
| level | UNGRADED | 未定级 | — | `{"rank":8}` |
| level | NONE | 无 | — | `{"rank":6}` |

`category_level` 字典定义每个类别允许哪些等级（如社区矫正只允许 HIGH/MID/LOW），用于表单与校验。

## 3 接口设计

### 3.1 通用约定

**基础路径**：`/api/v1`

**统一响应**：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "trace_id": "a1b2c3d4"
}
```

**分页响应**：

```json
{
  "code": 0,
  "data": { "items": [], "total": 6028, "page": 1, "size": 20 },
  "trace_id": "..."
}
```

**错误码规范**：

| 段 | 含义 | 示例 |
|---|---|---|
| 0 | 成功 | 0 |
| 1xxxx | 通用 | 10001 参数错误、10002 未登录、10003 无权限、10004 资源不存在、10005 状态冲突 |
| 2xxxx | 台账 | 20001 身份证号已存在、20002 标签数超限、20003 已消减不可编辑 |
| 3xxxx | 风险 | 30001 等级不允许下调、30002 距上次下调不足 30 日、30003 评估依据缺失 |
| 4xxxx | 导入 | 40001 模板不匹配、40002 文件解析失败、40003 批次处理中、40004 文件已导入 |
| 5xxxx | 权限 | 50001 明文导出需审批、50002 授权已过期、50003 申请人不能自审 |

**请求头**：`Authorization: Bearer <token>`、`X-Trace-Id`（可选）

## 4 关键流程设计

### 4.1 导入与查重并档

```
① 上传文件 → 计算 file_hash → 查 import_batch 幂等键
   命中 → 返回"该文件已导入（批次 xxx）"，终止
② 解析表头 → 与部门映射模板比对 → 不匹配则返回缺失/多余列清单
③ 逐行处理（每 500 行一个事务）：
   a. 落 raw_ledger（原始 JSON）
   b. 字段校验（必填、字典、格式、身份证校验位）
      失败 → process_flag=FAILED，收集错误
   c. 身份证号标准化 → 计算 id_card_hash
   d. 查 person（id_card_hash）
      不存在 → 新建 person（status=ACTIVE），插入 tag，flag=NEW
      存在   → 更新可变字段，插入 tag
               若同类别同部门已存在 → 合并（更新等级取高），flag=MERGED
               若不同部门同类别 → 插入第二条 tag，置 is_dual_reg，flag=MERGED
   e. 重算该人 tag_count / multi_tag_flag / dual_reg_flag / control_rank
④ 批量重算受影响人员的 control_level 与 key_flag
⑤ 写 import_batch 统计，生成错误明细
⑥ 异步触发 stat_daily 增量刷新
```

**性能要点**：身份证哈希与人员存在性检查用一次批量查询预加载（`WHERE id_card_hash = ANY(:hashes)`），避免逐行查询。

### 4.2 等级下调审批

```
① 属地/部门发起（risk:adjust:down）
   校验：标签存在且有效；目标等级低于当前；距上次下调 > 30 日；
        评估依据非空；附件 ≥1
② 创建 approval（type=LEVEL_DOWN）+ risk_change（status=PENDING）
③ 按规则路由审批人（见 07 文档 7.3）：
   低↔中 → 科室负责人；中↔高 → 分管领导；高风险降级 → 政法委
④ 审批通过：
   - risk_change.status=EFFECTIVE，写 effective_time
   - 更新 person_tag.level_code / std_risk_rank
   - 重算 person.control_rank / control_level / key_flag
   - 写审计日志
   - 触发 stat_daily 增量修正
   - 生成随访待办（30 日内未随访则预警）
⑤ 驳回：risk_change.status=REJECTED，通知申请人，记录驳回理由
```

### 4.3 驾驶舱指标聚合

```
每日 00:30 全量刷新 stat_daily(street_code='ALL' 及各镇街)
当日 09:00—20:00 每小时增量修正当日行（仅修正在册/消减/新增计数）

前端请求 → 读 stat_daily（当日无记录则回退到最近有记录日期）
         → 趋势/结构类指标直接查明细（数据量小，带索引）
         → 全部响应 ≤ 3 秒
```

**降级策略**：若 stat_daily 当日数据缺失，返回最近日期数据并带 `stale: true`，前端提示"数据截至 x 日"。

### 4.4 预警规则扫描

```
每日 06:00 全量扫描（可在后台手动触发）
规则（每条可独立开关、阈值可配）：
  R01 NO_VISIT_30       高风险 ≥30 日无走访
  R02 LOST_CONTACT      失访/拒访超 30 日
  R03 UNGRADED_30       未定级超 30 日
  R04 DUAL_UNCONFIRMED  双在册超 7 日未双部门确认
  R05 DOWN_NO_FOLLOW    下调后 30 日无随访
  R06 BASIS_MISSING     高风险但评估依据缺失
  R07 NO_BAOLIAN        高风险未指定包联干部

生成前查重：同一 person + rule 在 PENDING/HANDLING 状态已存在则跳过
指派：按 person.street_code → 属地经办；按 master_dept → 部门经办
```

### 4.5 明文导出审批与使用

```
① 申请（export:plain:apply）：人员范围、用途、有效期、预计条数
② 审批（export:plain:approve）：
   - 校验 approver ≠ applicant
   - >50 条或含未成年人 → 需第二个审批人（串行）
③ 通过后写 plain_grant：grant_id、user_id、scope(人员ID集合/条件)、
   expire_at、ip_whitelist、token
④ 导出时校验 grant：有效、未过期、条数未超、IP 匹配
⑤ 生成文件：脱敏字段转明文 + 隐形水印（账号+时间戳）+ 加密压缩包
⑥ 记录 export_task，写审计（含 grant_id）
⑦ 有效期到自动失效；可提前 revoke
```

## 5 审计触发器（关键表防篡改）

```sql
CREATE OR REPLACE FUNCTION fn_audit_protect() RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'DELETE' THEN
        RAISE EXCEPTION 'audit_protect: 禁止删除 %', TG_TABLE_NAME;
    END IF;
    IF TG_OP = 'UPDATE' AND TG_TABLE_NAME = 'risk_change' THEN
        IF NEW.from_level <> OLD.from_level
           OR NEW.to_level <> OLD.to_level
           OR NEW.applicant <> OLD.applicant THEN
            RAISE EXCEPTION 'audit_protect: 禁止修改历史字段';
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_risk_change_protect
    BEFORE UPDATE OR DELETE ON risk_change
    FOR EACH ROW EXECUTE FUNCTION fn_audit_protect();
```

`audit_log` 表通过权限控制：应用账号仅 GRANT INSERT，回收 UPDATE/DELETE。
