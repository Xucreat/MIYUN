## 1 方案目标与处理原则

### 1.1 目标

四部门台账在结构、命名、口径三个层面均不一致，无法直接汇入统一的人员档案库。本方案的目标是：**在不改变各部门现有报表习惯、不要求部门返工重填的前提下，把 15 份异构台账归一为一套可支撑"一人一档、风险分级、动态监测"的标准数据结构。**

### 1.2 三条处理原则

| 原则 | 含义 | 适用对象 |
|---|---|---|
| **求同** | 各部门都有的共性字段，抽取为统一主干字段，强制对齐 | 姓名、身份证号、性别、住址、联系方式等 |
| **存异** | 部门特有的业务字段，不做强行对齐，按类别挂载到扩展区，保留原始语义 | 诊断、列控级别、矫正类别、信访诉求等 |
| **分级裁剪** | 按"是否支撑区级管控决策"分三级处理：进入主干、进入扩展、仅留存原始 | 公安 64 列模板中的扩展信息、扬言表警情字段等 |

一句话概括：**主干只留"认人、定位、定级、定责"必需的字段，其余按类别存放，原始表全量留档。**

## 2 数据现状盘点

### 2.1 总体规模

| 部门 | 文件 | 表块数 | 字段位 | 表块构成 |
|---|---|---|---|---|
| 公安 | 公安.xls | **11** | 418 | 涉访群体、刑释不满五年、常住关注群体、六失一偏、精神障碍、邪教、社区矫正、吸毒、扬言、不良行为未成年人、涉访关注人员 |
| 司法 | 司法.xls | 2 | 22 | 社区矫正对象、安置帮教对象 |
| 卫健 | 卫健.xls | 1 | 27 | 严重精神障碍患者 |
| 信访 | 信访.xls | 1 | 18 | 信访关注人员 |
| **合计** | 4 个文件 | **15** | **485** | — |

去重后共 **253 个不同字段名**，其中**仅在两个及以上部门同时出现的只有 7 个**：姓名、身份证号、性别、户籍地址、年龄、联系方式、备注。

这组数字说明一个基本事实：**四个部门之间可以直接复用的字段不足 3%**。因此一致化工作不可能靠"字段对齐"完成，必须建立分层模型。

### 2.2 结构差异

| 差异维度 | 具体表现 | 影响 |
|---|---|---|
| 单文件多表块 | 公安一个文件内含 11 个业务表块，每块结构独立 | 导入时须按标题行切块，逐块绑定类别 |
| 列数跨度极大 | 最少 8 列（常住关注群体），最多 80 列（扬言人员） | 无法用统一列位置解析，须按表头名称映射 |
| 同构模板复用 | 刑释不满五年、社区矫正、吸毒、不良行为未成年人 4 块共用同一 64 列模板（含 28 列扩展信息） | 可用 1 套映射覆盖 4 类，降低工作量 |
| 粒度不一致 | "涉访群体""常住关注群体"为群体统计（含"群体涉及人数""活跃人数"），非个人台账 | 不能直接写入人员主档，须单独处理 |
| 一列多值 | 卫健"监护人姓名及电话""精防医生姓名及电话""镇街主管领导姓名及电话" | 须拆分为姓名、电话两字段 |
| 同名列重复 | 公安涉访关注表出现两个"联系方式"，分属责任领导与责任民警 | 须按位置区分，不能按名称匹配 |

### 2.4 口径差异（比命名差异更难处理）

| 差异点 | 各部门现状 | 处理方式 |
|---|---|---|
| 风险分级体系 | 公安：风险等级（高中低）／风险评估／人员级别／列控级别（一二三级）四种并用；信访：行为等级；卫健：危险度评估（0—5 级）+ 风险评估（高中低）双轨；司法：重点/一般两档 | 建立「类别+等级 → 统一风险序」映射表，部门原值完整保留 |
| 卫健双评估 | 同一患者同时有"目前危险度评估（级）"和"风险评估（高、中、低）"两个字段，含义不同 | 两个字段分别入库，不合并；定级以"风险评估（高、中、低）"为主，"危险度评估"作为特征字段 |
| 双在册识别 | 卫健表含"是否公安列管"字段，可直接判定；公安侧无对应字段 | 以卫健"是否公安列管"为正向标识，同时以身份证号碰撞做双向校验 |
| 失能人群口径 | 公安用"六失一偏"（失独、失业、失亲、失婚、失意、失管 + 心理偏执），信访用"是否三失一偏" | 信访"三失一偏"视为"六失一偏"的子集口径，不强行等同，分别落库并标注来源口径 |
| 类别命名 | 同一类人员在不同部门叫法不同（如公安"故意犯罪刑满释放不满五年"与司法"安置帮教对象"存在交叉） | 建立类别映射字典，允许一类人员来自多部门表块，以标签形式共存 |
| 状态语义 | 公安"列管状态""列撤管状态""调整状态"；信访"是否稳控"；卫健"是否人档分离" | 统一为"在册/已消减/已迁出"三态，原值保留在扩展区 |

## 3 一致化总体模型

### 3.1 三层字段模型

```
┌─────────────────────────────────────────────────────────────┐
│  L1 主干层（统一标准，22 个字段，强制对齐）                   │
│      认人：姓名、身份证号、性别、出生日期、民族               │
│      定位：户籍地址、现住址、责任镇街、社区/村                │
│      定级：人员类别、类别内等级、管控等级、统一风险序          │
│      定责：主责单位、责任民警/包联干部、列管状态、列入事由     │
│      留痕：列管时间、撤管时间、撤管原因、数据来源、更新时间    │
├─────────────────────────────────────────────────────────────┤
│  L2 类别扩展层（11 类各自专属，JSONB 存储，按类别挂载）       │
│      矫正类别/矫正期限、诊断/危险度、诉求/行为等级、           │
│      列控级别、组织类别、案件类别、帮教期、监护情况等          │
├─────────────────────────────────────────────────────────────┤
│  L3 原始留存层（不映射、不改写，全量存 raw_json）             │
│      公安 64 列模板的 28 列扩展信息、扬言表警情字段、          │
│      卫健救助类标志位、部门内部编码等                          │
└─────────────────────────────────────────────────────────────┘
```

**分层依据**：L1 是区级管控决策的最小必要集（少了就做不了统计与考核）；L2 是部门专业判断依据（区级要看，但不参与统一比较）；L3 是留档备查（出了问题能回溯，平时不展示）。

### 3.2 四种差异处理策略

| 策略 | 定义 | 应用示例 |
|---|---|---|
| **归并** | 多字段名指向同一概念，统一为一个主干字段，其余登记为别名 | 6 种身份证号叫法 → `id_card_no` |
| **拆分** | 一列内含多个信息，拆为结构化字段 | 卫健"监护人姓名及电话" → `guardian_name` + `guardian_phone` |
| **降级** | 专业字段不进主干，转入 L2 扩展区 | 公安"纳管（标注）事由详情" → 扩展区 |
| **裁剪** | 区级管理不需要、且涉公安专业业务，仅存 L3 不作展示 | 扬言表"警情摘要""工作照片""活跃度积分" |

## 5 分部门映射细则

### 5.1 公安（11 个表块）

#### 5.1.1 共用 64 列模板（4 个表块）

适用：故意犯罪刑满释放不满五年、社区矫正对象、吸毒人员、有严重不良行为未成年人。

| 类别 | 列号范围 | 处理 |
|---|---|---|
| 身份类（12—18 列） | 姓名、身份证号、手机号码、户籍地、现居住地、民族、性别 | → L1 主干 |
| 管辖类（1—6 列） | 列管状态、管辖分类、列管分局、列管派出所、列管社区、列管民警 | 列管状态→`list_status`；列管社区→`community`；列管民警→`cadre_name`；分局/派出所→L2 |
| 列管事由（7—11 列） | 纳管事由详情、列管依据、列管意见、人员类型、人口类别 | 事由→`list_reason`（L2 保留分项）；人员类型→L2 |
| 评价类（19—25 列） | 民警工作情况、最近现实表现情况、评价时间、评价结果、评价原因、评价人 | 评价结果→`level_code`（映射高中低）；其余→L2 |
| 等级（26 列） | 风险等级 | → `level_code`（主口径） |
| 案件类（27—35 列） | 打击处理时间、案件类别、处理单位、处理结果、入库时间、更新时间、撤管时间、撤管原因 | 撤管时间/原因→L1；入库时间→`list_date`；其余→L2 |
| 扩展信息（36—63 列） | 刑释扩展 4 列、所外监管 2 列、未成年 22 列 | → **L3 原始留存** |

**字段冲突处理**：同一人员同时存在"风险等级"（26 列）与"评价结果"（23 列）两个等级来源时，以"风险等级"为主口径，"评价结果"存入 L2 供研判参考。

#### 5.1.2 扬言人员表（80 列）

| 分组 | 列 | 处理 |
|---|---|---|
| 身份 | 当事人姓名、当事人身份证号、当事人联系电话、性别、年龄、民族、户籍地址、现住地 | → L1 |
| 等级 | 风险评估（15 列） | → `level_code` |
| 事由 | 警情标题、警情摘要、主要诉求、扬言类型 | 诉求→`list_reason`；警情信息→**L3 裁剪**（公安专业数据） |
| 责任 | 属地街镇、责任民警、责任领导姓名 | → `street_code`、`cadre_name` |
| 状态 | 扬言人员是否在账、是否见面、诉求状态 | → `list_status` |

## 7 特殊情形处理

| 情形 | 处理规则 |
|---|---|
| 群体级台账（涉访群体、常住关注群体） | 不进入人员主档。单独建"群体台账"表，字段原样保留；群体不参与"一人一档"统计，在驾驶舱单列"关注群体"指标 |
| 同名列重复（两个"联系方式"） | 映射配置按**列序号**定位，不按名称匹配；配置界面显示列序号与上级列名（责任领导/责任民警）以便区分 |
| 一列多值（姓名及电话） | 正则拆分；失败整列入 L2 并标记，不阻断导入 |
| 64 列模板的 28 列扩展信息 | 全部存入 `raw_json`；仅在档案详情页"专业信息"折叠区按权限展示，不参与统计 |
| 身份证号缺失 | 生成临时编号，标注待补，不计入去重率 |
| 同一人跨部门重复 | 按身份证号哈希碰撞合并为一人一档；同类别多来源分行存标签，形成双在册 |
| 部门内部编码（台账业务ID、关联人员id） | 存入 L3，用于回溯与后续接口对接 |
| 空值与"—""/""无" | 统一识别为 NULL；不将"—"作为有效值参与统计 |

## 8 落库流程

```
① 部门文件上传（.xls/.xlsx）
② 表块识别：扫描标题行（单非空单元格且列数>3），切分为 15 类表块
③ 表块 → 类别绑定：按标题关键词匹配（可人工调整一次并保存）
④ 字段映射：加载该表块映射配置（预置 + 可修改），按列序号绑定到 L1/L2/L3
⑤ 清洗：去空行、统一"—"为 NULL、日期格式归一、字典同义词转换、合并列拆分
⑥ 校验：身份证格式与校验位、必填项、字典合法性、镇街合法性
⑦ 写入：raw_ledger（原始 JSON）→ person（查重并档）→ person_tag（类别标签）→ person_ext（L2）
⑧ 重算：标签数、多标标识、双在册标识、管控等级、统一风险序
⑨ 报告：成功/失败/合并/新增标签四类计数 + 错误明细 + 已转换项清单
```

**幂等保障**：以"文件哈希 + 部门 + 表块"为幂等键，同一文件重复上传直接返回既有批次，不重复处理。

## 10 验收标准
