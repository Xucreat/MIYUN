## 1 开发策略

### 1.1 两阶段推进

| 阶段 | 目标 | 周期 | 数据 | 交付标准 |
|---|---|---|---|---|
| 一阶段 Demo | 可汇报、可演示的雏形 | 6 周 | 虚拟数据（6000 人量级） | 全流程跑通，演示无报错 |
| 二阶段建设 | 正式可用系统 | 约 16 周 | 四部门真实数据接入 | 通过等保测评与验收 |

**关键原则**：Demo 不是"做个样子"，而是建设期的**第一个可用版本**。所有核心表结构、权限模型、脱敏机制、审计机制在 Demo 期即定型，后续只做功能增量，不做架构重写。这样 Demo 通过后可直接进入建设，避免二次开发。

### 1.2 开发顺序策略

按"**数据 → 权限 → 业务 → 展示**"的顺序推进，而非按页面顺序：

1. 先做数据模型与虚拟数据生成器——没有数据什么都验证不了；
2. 再做权限与脱敏骨架——后加权限等于全部返工；
3. 然后业务功能（台账、风险、导入）；
4. 最后驾驶舱与导出——展示层最容易调整，放后面做不浪费。

### 2.2 后端分层约定

| 层 | 职责 | 禁止 |
|---|---|---|
| `api` | 参数校验、权限依赖声明、调用 service、组装响应 | 写业务规则、直接操作 ORM |
| `service` | 业务规则、事务边界、跨模块编排 | 处理 HTTP 细节 |
| `repository` | 数据访问、查询构造（含数据范围注入） | 写业务判断 |
| `models` | ORM 表定义 | 写业务方法 |
| `schemas` | Pydantic DTO，含脱敏输出模型 | 直接暴露 ORM 对象 |

**关键约定**：数据范围过滤只在 `repository` 层统一注入，通过 `QueryScope` 对象传递，禁止在各个接口里手写 `where street_code in (...)`——这是权限漏配的主要来源。

## 3 技术规范

### 3.1 后端规范

| 项 | 规范 |
|---|---|
| 命名 | 模块 snake_case；类 PascalCase；常量 UPPER；接口路径用复数名词（`/api/v1/persons`） |
| 接口风格 | REST；列表统一返回 `{items, total, page, size}`；统一响应包装 `{code, message, data, trace_id}` |
| 错误码 | 五位数字：`1xxxx` 通用、`2xxxx` 台账、`3xxxx` 风险、`4xxxx` 导入、`5xxxx` 权限；错误信息中文面向业务人员 |
| 分页 | `page`（从 1 起）+ `size`（默认 20，上限 200）；深分页用 `cursor` |
| 时间 | 统一 `Asia/Shanghai`，接口返回 ISO8601 带时区 |
| 事务 | service 层显式 `async with session.begin()`；导入按 500 行分批 |
| 日志 | JSON 结构化，字段：`ts/level/trace_id/user_id/path/cost/result`；禁止打印身份证号、姓名、手机号原文 |
| 配置 | `pydantic-settings` 从 `.env` 读取；密钥类不进代码库，`.env.example` 只给键名 |
| 迁移 | 所有 DDL 变更走 Alembic，禁止手工改库；迁移脚本需可回滚 |

### 3.2 前端规范

| 项 | 规范 |
|---|---|
| 组件 | `<script setup lang="ts">`；单文件组件命名 PascalCase；业务组件前缀 `Zdr`（如 `ZdrPersonCard`） |
| 路由 | 路由表按模块拆分，`meta.perms` 声明所需权限，守卫统一校验；未授权路由不注册（而非进入后拦截） |
| 权限指令 | `v-perm="'person:export:plain'"` 控制按钮显隐；无权限时按钮不渲染 |
| 脱敏展示 | 统一使用 `<MaskedText field="id_card_no" :value="row.id_card_no" />`，**禁止在模板里手写掩码逻辑** |
| 图表 | 统一经 `BaseChart` 封装，负责 resize、theme、loading、空态；页面只传 option |
| 状态 | Pinia；用户态、字典态全局；列表筛选态留在组件内 |
| 请求 | axios 实例统一注入 token、trace_id、错误提示；401 跳登录、403 提示无权限 |
| 样式 | 设计变量集中在 `variables.css`；不引入外部字体与 CDN；大屏单独主题 |
| 大屏适配 | 1920×1080 设计稿 + `scale` 等比缩放；Pad 断点 `<1200px` 切单列 |

### 3.3 Git 规范

- 分支：`main`（可发布）、`develop`（集成）、`feature/<模块>-<简述>`、`hotfix/<简述>`；
- 提交信息：`<type>(<scope>): <subject>`，type ∈ feat/fix/docs/style/refactor/test/chore/build；中文描述；
- 合并：feature → develop 走 MR，至少 1 人评审；develop → main 需通过全部测试 + 演示验收；
- 禁止直接向 main 推送；禁止提交 `.env`、密钥、真实数据文件。

## 9 质量保障

### 9.1 代码质量

- 后端：`ruff`（lint + format）+ `mypy`（类型检查，核心模块强制）；
- 前端：`eslint` + `vue-tsc` 类型检查；
- 提交前本地钩子（pre-commit）执行 lint 与单测；
- MR 需 1 人评审，评审重点：权限是否漏注入、日志是否打印敏感信息、SQL 是否走索引。

### 9.2 测试

| 类型 | 范围 | 门槛 |
|---|---|---|
| 单元测试 | 风险序计算、查重并档、脱敏、风险等级变动 | 核心模块覆盖率 ≥70% |
| 接口测试 | 全部 API，含权限矩阵用例 | 全通过 |
| 权限测试 | 三角色 × 关键接口，验证越权被拒 | 零越权 |
| 性能测试 | 组合查询、驾驶舱、6000 行导入 | 达 SRS 8.2 |
| 安全测试 | 漏洞扫描、越权、注入、敏感信息泄露 | 高危清零 |

### 9.3 演示质量

Demo 版本额外要求：演示路径上无空数据页、无未完成按钮（未完成功能隐藏而非置灰）、无英文报错、断网可演示（数据本地）。
