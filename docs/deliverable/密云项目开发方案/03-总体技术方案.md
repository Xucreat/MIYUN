## 1 概述

### 1.1 方案目标

在满足等保三级、数据不出域、本地化部署的前提下，用最短周期交付可汇报、可演示、可持续演进的重点人员台账管理系统。方案需同时满足两个时间尺度的要求：**Demo 期**（2026 年底前，虚拟数据跑通全流程）与**建设期**（四部门数据接入、月度报送闭环、等保测评）。

### 1.2 方案依据

《需求规格说明书》（MY-ZDRY-SRS-001）第 6、7、8 章；《数据字段标准与脱敏规范》（MY-ZDRY-DATA-002）；GB/T 22239-2019 网络安全等级保护基本要求（第三级）。

## 2 设计原则与关键约束

| 原则 | 落地做法 |
|---|---|
| 不过度设计 | 一期采用**模块化单体**，不拆微服务、不引入消息队列、不引入 Elasticsearch。6000 人、百万级日志的量级，单套 PostgreSQL 完全覆盖 |
| 数据不出域 | 全栈本地化；不调用外部 AI 接口；地图底图使用本地化矢量数据；前端不引用境外 CDN/字体 |
| 前后端分离 | 前端 SPA + 后端 REST API，接口即边界，便于后续被大屏、移动端复用 |
| 字典驱动 | 类别、等级、规则、镇街、部门均可配置，新增第 12 类人员不改代码 |
| 密级内建 | 脱敏在服务层统一拦截（序列化器），不在各页面各写一套 |
| 可升级信创 | 数据库访问经 ORM 抽象，预留达梦/人大金仓适配；不依赖 PG 专有语法（除 JSONB、pg_trgm 等可替代特性） |

**一期明确不做**：微服务拆分、服务网格、容器编排集群、分布式缓存、实时计算、双活多活。以上在数据量或并发出现数量级变化时再评估。

| 层次 | 选型 | 版本基线 | 选型理由 |

| 前端框架 | Vue 3 + TypeScript + Vite | Vue 3.4+ | 团队熟悉度高，生态成熟，构建快；大屏与表单场景都有成熟组件 |

| AI 推理 | 本地部署 GLM 系列（可选） | 视算力 | 关键词提示、摘要生成；Demo 期用规则词典替代，不强依赖 |
| 部署 | Docker Compose | — | 单机/双机即可；不上 K8s |
| 反向代理 | Nginx | — | 静态资源、TLS 卸载、限流 |

### 4.2 关键取舍说明

**为什么不上 Elasticsearch**：检索需求集中在人员姓名（6000 条）、身份证号（精确）、标签与等级（枚举）、镇街（枚举）。PG 的 B-tree + GIN + pg_trgm 足够，且少一套组件就少一份等保测评对象和运维负担。若后续接入十万级外来人员筛查再评估。

**为什么不上 Redis**：一期无高频写入热点，会话用 JWT 无状态，字典变更频率以周计。

**为什么模块化单体而非微服务**：团队规模与交付周期不支撑微服务运维成本；模块边界用 Python 包 + 明确服务接口划分，后续确需拆分时按域切出即可。

**为什么不用在线地图**：涉密/敏感场景下，人员分布不应请求外部瓦片服务。采用本地 GeoJSON 行政边界（区—镇街两级，来自标准地图服务，需具备审图号）配合 ECharts geo 渲染；如需底图细节，在区内网部署天地图离线瓦片服务。

## 5 数据架构

### 5.1 数据分层

| 层 | 内容 | 说明 |
|---|---|---|
| ODS 原始层 | `raw_ledger` | 部门报送 Excel 原样落库（含原始 JSON），永不修改，供回溯与差异比对 |
| DWD 明细层 | `person` / `person_tag` / `person_ext` / `visit_record` / `risk_change` | 清洗、查重、并档后的业务主数据 |
| DWS 汇总层 | `stat_*` 汇总表（日快照） | 驾驶舱指标预聚合，避免大屏每次实时聚合 |
| ADS 应用层 | 报表、导出、接口输出 | 按角色脱敏后输出 |

### 5.2 核心数据流

```
四部门 Excel/接口
      │
      ▼
[导入引擎] 解析 → 表头映射 → 字段校验 → 落 raw_ledger
      │
      ▼
[查重并档] 身份证标准化 → 主档匹配 → 新增/合并 → 标签写入 → 双在册与多标标识
      │
      ▼
[风险序计算] 类别+等级 → 归一风险序 → 就高不就低 → 更新主档 control_level
      │
      ├──▶ [预警规则引擎] 定时扫描 → 生成待办
      │
      ▼
[日汇总任务] 生成 stat 快照 → 驾驶舱读取
      │
      ▼
[审计] 全链路操作日志
```

### 5.3 关键数据设计要点

1. **主档瘦身**：主档只存 28 个核心字段，类别专属字段进 `person_ext.detail`（JSONB），避免宽表。
2. **标签独立成表**：等级与列入原因属于"标签"而非"人"，一人多标时各自独立审批与留痕。
3. **变动留痕**：`risk_change` 记录 from/to 等级、依据、申请人、审批人，是"调整可追溯"的物理载体。
4. **日志分区**：`audit_log` 按月分区，保留 6 个月以上，历史分区可归档导出。
5. **汇总预计算**：驾驶舱 6 个指标的日快照表，避免每次全表扫描；当日数据用增量修正。

## 7 关键技术方案

### 7.1 一人一档与查重并档

- 主键标准化：身份证号去空格、末位 X 大写、校验位验证。
- 匹配策略：**身份证号精确匹配为主，不做模糊匹配**。姓名+出生日期仅用于"疑似重复"提示（人工确认），绝不自动合并——错并的代价远高于漏并。
- 并档事务：单条记录处理在一个事务内完成主档 upsert、标签 upsert、标识重算、变动记录写入，失败整体回滚。
- 幂等：导入批次按"文件哈希 + 部门 + 类别"做幂等键，重复上传同文件给出提示，避免重复计数。

### 7.2 统一风险序

不同类别分级口径不同（高中低 / A-B-C / 一二三级 / 关注对象 / 风险不详 / 未定级 / 无），跨类别无法直接比较。方案：

1. 维护字典表 `dict_level_map`：`(category_code, level_code) → std_risk_rank`，rank 取 1~9，1 最高。
2. 主档 `std_risk_rank = min(该人所有有效标签的 rank)`，即最高的那个。
3. `control_level` 取该 rank 对应的管控等级中文名，用于展示。
4. "高风险及以上"口径 = `std_risk_rank ≤ 3`，阈值可配置。
5. 风险不详、未定级单独赋 rank（如 8/9），**不参与"高风险"统计但单列**，避免被误当作低风险管理。

详见《07-业务规则与风险分级口径说明》。

### 7.3 组合查询性能

- 索引：`person(id_card_no)` 唯一；`person(street_code, std_risk_rank)`、`person(status)`、`person_tag(category_code, level_code)` 组合索引；姓名 `gin_trgm_ops` 支撑 `LIKE '%x%'`。
- 拼音检索：主档冗余 `name_pinyin`（全拼）与 `name_initials`（首字母）两列，导入/变更时由 pypinyin 生成，走前缀索引。
- 标签组合查询（同时含 A 和 B / 含 A 不含 B）：用 `EXISTS` 子查询或 `GROUP BY person_id HAVING array_agg(category_code) @> ARRAY[...]`，6000 人量级毫秒级。
- 列表分页统一 `LIMIT/OFFSET`，深分页时改用游标（keyset）分页。
- 驾驶舱指标读 DWS 汇总表，不读明细。

### 7.4 驾驶舱与地图

- ECharts `geo` 组件加载本地 `miyun.json`（区界 + 20 个镇街面），按 `street_code` 关联指标渲染 visualMap 热力。
- 下钻：点击镇街 → 前端切换 geoJSON 到该镇街社区级（若有）或右侧联动明细列表。
- 大屏适配：基于 1920×1080 设计稿做 `transform: scale()` 等比缩放 + 关键区域栅格自适应，Pad 横屏切单列布局。
- 图表数据统一走 `/api/analytics/*`，返回结构与 ECharts option 解耦（后端只返回数据，前端组装 option），便于换图表库。
- **合规**：底图使用具备审图号的标准地图矢量数据，页面显著位置标注审图号；不使用境外地图服务与境外 CDN。

### 7.5 导入引擎

六步流水线：`解析 → 表头映射 → 类型与字典校验 → 行级去重 → 查重并档 → 结果回写`。要点：

- 逐行处理 + 分批提交（每 500 行一个事务），避免单事务过大。
- 错误不中断整批：错误行收集到 `import_error`，成功后返回"成功/失败/合并"三类计数与失败明细下载。
- 长任务异步化：>2000 行的导入转为后台任务，前端轮询进度（进度百分比 + 已处理行数）。
- 原始文件留存：源文件存入对象存储/本地目录，批次记录 fingerprint，支持"下载原文件"。

### 7.6 权限模型

RBAC + 数据权限双层：

- **功能权限**：角色—菜单—按钮（如 `person:export:plain`）。
- **数据权限**：角色绑定数据范围表达式，支持四种：全区 / 指定镇街集合 / 指定部门 / 本部门。落地为 SQL 层的 `WHERE` 注入（同一套查询构造器统一加条件，避免漏加）。
- **字段权限**：脱敏在 Pydantic 序列化层统一处理——同一 ORM 对象按请求上下文中的角色密级输出不同字段形态，页面不参与脱敏，防止绕过。
- 高危操作二次校验：明文导出、批量删除、权限变更要求"当前账号 + 另一管理员"双因子确认。

详见《08-角色权限矩阵》。

### 7.7 审计

- 应用层中间件记录：操作人、IP、UA、时间、接口、业务对象、结果、耗时。
- 业务层显式埋点：查看档案、导出、等级调整、权限变更，记录到 `audit_log`（含被访问人员编号）。
- 数据库层触发器兜底：主档与标签表的 UPDATE/DELETE 强制写变更前后值。
- 日志表只允许 INSERT，应用账号无 UPDATE/DELETE 权限；运维查看走只读账号。

### 7.8 AI 能力（可选，非强依赖）

| 场景 | 实现 | 说明 |
|---|---|---|
| 涉稳关键词提示（FR-YJ-04） | 本地词典 + 规则匹配为主 | Demo 期即可用，零算力成本；命中后人工确认 |
| 走访记录摘要 | 本地 GLM 小模型（如 9B 量化） | 输入为脱敏文本，模型部署在区内网 |
| 研判意见初稿 | 同上 | 输出仅为草稿，需人工修改确认 |

**红线**：实名数据（身份证、姓名、住址、诊断、案件）不进入任何外部模型接口；本地模型服务与业务库同域部署，走内网调用；AI 结论一律标记"AI 辅助，需人工确认"，不自动定级、不自动消减。

## 11 技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 部门表头差异大、脏数据多 | 导入失败率高、口径不准 | 映射模板 + 同义词字典 + 待核实池；首轮导入由业务方陪跑 |
| 分级口径不统一（跨部门同名不同义） | 风险序失真、统计口径争议 | 风险序映射表由政法委确认后固化，写入字典并版本化 |
| 等保三级测评周期长 | 影响上线时间 | Demo 期即按三级要求做设计（日志、双因子、审计、加密），测评材料同步准备 |
| 地图数据合规 | 演示被叫停风险 | 使用有审图号标准地图；不使用境外服务 |
| 实名数据安全事件 | 政治与法律风险 | 数据不出域、最小必要、全程审计、明文导出双人复核 |
| 与公安系统功能重叠质疑 | 立项受阻 | 在方案与汇报中显性说明边界（管理台账 vs 专业研判） |
| Demo 认可后需求扩张 | 工期失控 | 需求基线化管理，新增需求走变更单，不在 Demo 期承接 |
