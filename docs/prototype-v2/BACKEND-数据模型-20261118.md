## 0. 结论先行

| 项 | 建议 | 理由 |
|---|---|---|
| 技术栈 | **FastAPI + SQLAlchemy 2.0 + PostgreSQL 16 + Alembic** | 与既有舆情系统同一套（可复用鉴权/审计/分页经验）；PG 支持部分索引、`jsonb`、`citext`，48 权限位与 jsonb 结构化配置都能吃下 |

## 3. 派生层：视图而非表

### 3.1 人员视图 `v_person_full`
`person` + `person_tag` 聚合 + `dual_confirm` 存在性 + `visit` 聚合，还原出前端 `p` 对象的全部字段（`tags` 数组、`multi`、`dual`、`visitGap`、`visitTotal`、`age`）。**前端契约不变**。

### 3.2 部门维度 `v_dept_stats`
两条 SQL 分开写（裁决 B1）：

```sql
-- 主责口径（486 单值）
SELECT primary_dept_id, count(*) FROM person GROUP BY 1;
-- 类别归属口径（667 人次）
SELECT dept_id, count(*) FROM person_tag GROUP BY 1;
```
两两重合见 §3.3；`multi_persons`（168）= `person_tag` 按 `person_id` 分组 `count(DISTINCT dept_id) > 1`。

### 3.3 双在册交叉 `v_dual_cross`
```sql
-- 交叉 50 / 并集 245（与 data.js deptStats() 同算法）
WITH cross AS (
  SELECT person_id FROM person_tag GROUP BY 1 HAVING count(DISTINCT dept_id) > 1
), dual AS (SELECT DISTINCT person_id FROM dual_confirm)
SELECT count(*) FILTER (WHERE d.person_id IS NOT NULL) AS inter,
       (SELECT count(*) FROM dual) + (SELECT count(*) FROM cross) - count(*) FILTER (WHERE d.person_id IS NOT NULL) AS union
FROM cross c LEFT JOIN dual d USING (person_id);
```

### 3.4 指标快照 `metric_snapshot`
`as_of` + 16 个计数列（`in_register` `high_plus` `mid` `low` `unknown` `dual` `multi` `multi2` `multi3` `high2` `no_basis` `no_visit30` `no_visit30_high` `off_register` `month_add` `month_sub` `ledger_records`）。
职责：承载**没有逐人明细**的两档（中 2,284 / 低 2,646），以及盲区去重 `887` 这类跨表口径。**唯一写入口 = 定时任务重算**，页面只读。

## 5. 种子数据策略（已定：S1 明细 + 快照）

现状：`persons` 只有 486 行（高风险及以上）+ `unrated` 612 行 = **1,098 行明细**；中风险 2,284 / 低风险 2,646 **没有明细，只有总数**。

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **S1（推荐）明细 + 快照** | 入 1,098 行明细；中/低两档由 `metric_snapshot` 承载 | 不造假数据；与前端现状 100% 一致；聚合可交叉验证（486 = persons 计数） | 人员台账分页只能翻到 1,098 条，与"在册 6,028"存在解释成本 |
| S2 生成补齐 | 用现有生成器（`mulberry32`）再合成 4,930 行中/低风险人员 | 台账可分页 6,028 条，聚合全可算 | 要新造 4,930 个身份证/姓名，后续接真实数据时必须整批清掉 |

若选 S2，`level` 分布须锁定 `mid=2284 / low=2646`，否则前端所有数字漂移。

## 6. 硬约束（来自裁决，写进迁移脚本注释）

1. **`level_change` 不建审批状态机** —— 只有 `status='已生效'` + `notified` 两个状态位。禁加 `approval_status` / `current_node` / `approver_chain`。
2. **`dual_confirm` 与 `person_tag` 不联动** —— 禁止触发器/物化同步。两者交叉 50、并集 245，含在一起会连锁改掉盲区 `887`（该值硬编码在 9 处）。
3. **`person.primary_dept_id` 单值 + `person_tag.dept_id` 多值** —— 两个维度都留，聚合 SQL 分开写；前端 `?dept=`（主责）与 `?deptTag=`（标签）已分好，后端不得合并成一个参数。
4. **`approve` 权限位保留**，语义 = 明文导出审批，不得用于业务审批门控。

### 10.2 三个「宁可少给」的裁决

| 争议点 | 裁决 | 理由 |
|---|---|---|
| 前端 half 权限（明文导出 / 减册 / 明文申请） | **一律按拒绝处理** | `role_perm` 只存「允许」，half 没入库；此时若按「未知=允许」会直接放行明文导出 |

### 10.3 写 API 的服务端权威

三个写操作（等级变动 / 走访 / 预警处置）里，下列字段**客户端传什么都不采信**：

- `rule`（定级责任）与 `approver`（登记人）—— 由过渡对（如 `high>high2` → 「部门集体会商 + 双签」）
  加 `dept.head` 生成，避免台账里「谁定级的」可被随手填。
- `by` / `role` / `ip` / `at`（审计四要素）—— 全部服务端填。
- `from`（原等级）—— 取库内当前值（`SELECT ... FOR UPDATE` 锁行）。

权限按**动作方向**判：`order(to) < order(from)` = 风险升高 → `risk:adjust:up`，反之 `risk:adjust:down`。
所以 R4（只有 up）能上调、下调被拒。

### 10.4 一处口径修正

（与 `data.js recalcStats()` 语义一致），其余仍取 `metric_snapshot`。
不这么改，登记一次等级变动后仪表盘数字不会动，等于写 API 白写。出参新增 `liveFields` 显式标注哪几个数是实时口径。

## 11. 实施结果（B5 已落地，2026-11-18）

**结论先行**：页面代码一行没改就接上了服务端。做法是「**快照 + 就地注入**」——
`assets/api.js` 在 `data.js` 之后、`store.js` 之前，**脚本解析期**同步读 sessionStorage 里的快照，
调 `DATA.hydrate()` 把 `persons / unrated / alerts / CHG_FULL / stats` 原地改写（数组引用不变）。
所以 14 个页面里没有一处 `if (live)` 分叉，也没有一个页面被改成异步引导。

### 11.1 为什么是快照，不是每页 fetch

| 方案 | 问题 |
|---|---|
| 每页 `fetch` 异步引导 | 要改 14 个页面的引导代码，首屏必闪，且任一页漏改就静默回落 |
| **快照 + 同步注入（采用）** | 只在 `api.js` 一处做异步，页面保持同步渲染语义 |

刷新语义：快照存 `sessionStorage`（按标签页隔离），带 `base` 指纹——换环境自动作废；
`?refresh=1` 强制重拉；`?live=1/0` 显式开关数据源；断网时 `status().offline = true`，顶栏变橙标并保留本地演示数据（不静默）。

### 11.2 改动清单

|---|---|---|

### 11.3 三处「必须按服务端口径」的映射

1. **身份**：`/api/me` → `ROLES.live`（scope / fields / can）。`STORE.role()` 在 live 下优先返回它，
   `can()` 直接读 `role_perm`，**不再叠加前端权限矩阵** —— 两份矩阵同时生效必然出现「前端能点、后端 403」。
2. **掩码**：脱敏已在服务端按 `field_policy` 做完，`field()` 的 live 分支只做「隐」字段遮挡 + `maskedFields` 标记，
   **绝不二次掩码**。二次掩码会把「任**」再掩一遍，前端显示与接口返回值就对不上。
3. **预警**：本地富文案当骨架、服务端状态当权威，按 id 合并。
   原因：B1 的 `alert` 表只存 `dept_id`（映射不上四个行业部门就是 NULL），整表替换会掉「鼓楼街道综治中心」这类责任单位原文。
   这是 B6 要补 `alert.dept_raw` 的动机。

### 11.4 一个必要的后端小改（零迁移）

`/api/persons` 出参新增 `visitTotal`（`(SELECT count(*) FROM visit v WHERE v.person_id = p.id)`）。
档案页要显示「走访次数」，本地原来是 `int(3,28)` 随机数，接真链路后取 `visit` 表实数（每人 6 条），
不改就是「明细 1,098 条但每人写了 0 次走访」。
