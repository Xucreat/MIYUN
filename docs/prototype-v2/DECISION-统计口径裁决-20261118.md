## 1. 口径 A：双在册 127 vs 跨部门共管 168

### 1.1 现状实测（`node` 直跑 `data.js`，非估算）

| 集合 | 定义 | 人数 | 数据来源 |
|---|---|---|---|
| 双在册 | `p.dual === true` | **127** | `data.js:206-209`，按 `towns[].d` 逐镇街均匀抽样打标 |
| 跨部门共管 | `deptsOf(p).length >= 2` | **168** | `data.js:472`，由 `TAGS[].dept` 映射派生 |
| 交集 | 既是双在册、标签又横跨 ≥2 部门 | **50** | 实测 |
| 并集 | 与「跨部门协同」有关的人 | **245** | 127 + 168 − 50 |
| 双在册 ∩ 多标 | `p.dual && p.multi` | **66** | `data.js:236-250` 等量置换刻意对齐的常数 |

**关键事实：127 与 168 只交 50（39%）**。原因是两者由**两条互不相干的生成路径**产出：

- `dual` 按**镇街**抽样（每镇按 `d` 值均匀取人），与标签无关；
- `168` 由**标签映射**算出，标签数是打散随机分配的（28 人 3 标 / 186 人 2 标 / 272 人 1 标）。

所以现在这个 39% 是"随机撞出来的"，不是业务设计的结果。演示时若被追问「这 127 人里有多少是跨部门共管的」，答案是 50——**能答，但答完要解释为什么这么低**。

### 1.2 业务上到底该是什么关系

这是裁决的核心，必须说清：

| | 双在册 | 跨部门共管 |
|---|---|---|
| 性质 | **确认状态**（谁已经在册） | **属性计算**（标签涉及哪些部门） |
| 产生方式 | 两部门**走台账流程**分别确认在册后打标 | 由人员的类别标签自动归并 |
| 是否可计算 | ❌ 不可，靠人工确认动作 | ✅ 可，纯派生 |
| 变更时机 | 部门确认 / 撤管时 | 标签增删时 |
| 现实关系 | **不必是子集**：某人在 A、B 两部门在册，标签可能只有 1 个（只打了"涉访"）；反之标签横跨两部门的人，未必都完成过双在册确认 | 同左 |

**结论：二者是正交的两个维度，"127 必须 ⊆ 168"不是业务真命题。**交叉 50 人、并集 245 人，在业务上完全讲得通。

### 1.3 方案 A1（推荐）：两套标记并存，UI 分层表述

**做法**

| 层 | 改动 |
|---|---|
| 数据 | 不动。`p.dual` 与 `deptsOf()` 保持现状 |
| UI 表述 | 侧栏口径弹窗（`shell.js`）把两行改成并列且互证的三行：<br>① 双在册确认 **127** 人 — 两部门均走台账确认在册后打标，**与标签无关**<br>② 跨部门共管 **168** 人 — 按类别标签映射，一人可命中多部门<br>③ 两者交叉 **50** 人 · 合计涉及 **245** 人 |
| 部门卡脚注 | 保留现有「跨部门共管 168 人 · 合计 667 人次（486 人）」，追加「与双在册 127 人交叉 50」 |
| 后端 | 两个独立字段/表：`person.dual_confirm(bool)` + `person_tag(person_id, tag_id)`；**不做任何外键关联** |

**为什么推荐**

1. 成本 0，纯文案；不动数据就不会牵动 `887` 等式。
2. **它就是真实系统的样子**——政务台账里"双在册标记"和"标签归属"本来就分属两个模块维护，后端建表时也天然是两处。做成子集反而是给演示数据加了一个现实中不存在的约束。
3. 交叉 50 / 并集 245 这两个数是**可以主动讲的加分项**：说明「系统能区分确认状态与属性归属，不是一锅炖」。

### 1.4 方案 A2（不推荐）：让 127 ⊆ 168

**做法**：`dual` 改为「从 `deptsOf(p).length >= 2` 的人群中抽 127 人」。

**为什么看起来诱人**：一句话就能讲通——「127 人双在册，全部纳入跨部门共管 168 人」。

**真实代价（这是把它列出来的原因）**

`deptsOf(p).length >= 2` ⟹ `p.tags.length >= 2` ⟹ `p.multi === true`。
所以改造后 **`dual ∩ multi` 会从 66 涨到 127**，于是盲区去重公式崩掉：

```
现在：887 = 127（双在册）+ 214（多标）+ 612（未定级）− 66（交集）
改造：826 = 127 + 214 + 612 − 127     ← 887 → 826
```

而 `887` 是**硬编码**在 9 处的展示口径：

| 文件 | 位置 |
|---|---|
| `data.js` | `:231` 注释、`:706` 段注释、`:708` `total: 887` |
| `page-blind.js` | `:8` 头注释、`:776` 盲区成因分布注释 |
| `blind.html` | `:127` 页头「887 人待核查」、`:184` 清单标题 |
| `index.html` | `:249` 模块描述、`:250` 标签、`:342` 流程图环节 9 |

连带影响：盲区三类卡片计数、成因分布图、核查任务闭环率（61.4% 的分母）、驾驶舱盲区卡、看板双在册卡。**这是一次跨 8 个文件的口径重算，且改完要重新跑一遍全站回归。**

**判断**：为了消除一个"业务上本来就不成立"的直觉，付出推翻一个核心指标的代价——不划算。除非业务方明确要求"127 必须是 168 的子集"并愿意承担 887 变更。

### 1.5 方案 A3（不推荐）：取消 168 的并列展示

部门卡只显示「667 人次 / 486 人」，不提跨部门共管。

**代价**：D3 决议「部门维度」的立论基础就是"一人涉多部门"，取消 168 等于自废叙事；且 `page-persons.js` 的 `?deptTag=` 深链、驾驶舱重合矩阵都建立在这个概念上。

## 2. 口径 B：主责单位 486 vs 类别归属 667 人次 / 168 人

### 2.1 现状实测

| 部门 | `p.dept` 主责单值 | 标签映射（人次） | 差额 |
|---|---|---|---|
| 公安分局 | 190 | 246 | +56 |
| 区司法局 | 125 | 167 | +42 |
| 区信访办 | 101 | 148 | +47 |
| 区卫健委 | 70 | 106 | +36 |
| **合计** | **486（= 在册明细人数）** | **667（人次）· 去重 486 · 跨部门 168** | **+181** |

每个部门都是**增益**（标签值 > 主责值），说明标签映射是主责单位的**业务超集**——一个人主责在司法局，同时可能涉访、涉稳。**这不是矛盾，是两个维度。**

### 2.2 真正的病根：一个词"部门"被复用了两次

| 前端入口 | 语义 | 命中数 | 现状 |
|---|---|---|---|
| 人员台账 `?dept=公安分局` | 主责单位（单值） | 190 | ✅ 正确 |
| 驾驶舱部门卡「公安分局 246」点击 | 类别归属（人次） | 246 | ✅ 已在 S6 改为 `?deptTag=` 深链，避免"点 246 进去只有 190 人" |

**S6 已经修过了**：`page-persons.js` 新增 `?deptTag=A,B`（多部门 AND 筛选），部门卡走 `deptTag`，台账筛选项走 `dept`。所以前端层面这块**已经定了**，本文只是把它固化成后端口径。

### 2.3 方案 B1（推荐）：双字段落库，命名强制区分

**表设计（这就是补后端要的东西）**

```sql
-- 主责单位：一人一个，行政归属
ALTER TABLE person ADD COLUMN primary_dept_id BIGINT REFERENCES dept(id);

-- 类别归属：一人多个，业务涉及
CREATE TABLE person_tag (
  person_id BIGINT NOT NULL REFERENCES person(id),
  tag_id    BIGINT NOT NULL REFERENCES tag(id),
  source    VARCHAR(16),   -- 导入 / 人工追加 / 规则命中
  created_at TIMESTAMPTZ,
  PRIMARY KEY (person_id, tag_id)
);
CREATE INDEX ix_person_tag_tag ON person_tag(tag_id);

-- 标签 → 部门 的映射（现有 TAGS[].dept 的落库形态）
ALTER TABLE tag ADD COLUMN dept_id BIGINT REFERENCES dept(id);
```

**两条聚合 SQL 必须分开写，不许混用**

```sql
-- ① 主责分布（答 190/125/101/70，合计 486）
SELECT d.name, COUNT(*) FROM person p JOIN dept d ON p.primary_dept_id = d.id
WHERE p.in_register GROUP BY 1;

-- ② 类别归属人次（答 246/167/148/106，合计 667）
SELECT d.name, COUNT(*) AS times
FROM person_tag pt JOIN tag t ON pt.tag_id = t.id JOIN dept d ON t.dept_id = d.id
WHERE pt.person_id IN (SELECT id FROM person WHERE in_register) GROUP BY 1;

-- ③ 跨部门共管人数（答 168）
SELECT COUNT(*) FROM (
  SELECT pt.person_id FROM person_tag pt JOIN tag t ON pt.tag_id = t.id
  GROUP BY 1 HAVING COUNT(DISTINCT t.dept_id) >= 2
) x;
```

**命名约定（写进 API 契约，防止下次又混）**

| 字段/参数 | 语义 | 类型 |
|---|---|---|
| `primary_dept` / `?dept=` | 主责单位，单值 | 标量 |
| `dept_tags` / `?deptTag=` | 类别归属，多值 | 数组 |
| 卡片标题 | 「按类别归属（人次）」 | 必带"人次"二字 |
| 台账筛选项 | 「主责单位」 | 不带"类别" |

### 2.4 方案 B2 / B3（均不推荐）

- **B2 只留主责单位**：部门卡数字变成 190/125/101/70 合计 486，与明细完全对得上，最"干净"。但**丢掉 D3 决议的核心叙事**（一人涉多部门 → 需要跨部门协同），且驾驶舱重合矩阵、`?deptTag=` 全部作废。
- **B3 只留标签归属**：`p.dept` 在 `assets/*.js` 有 **83 处**消费方（预警转派、包联责任人、镇街归属、报送质量、权限 view 收敛…），全部要改。不现实。

| `tag` | `DATA.TAGS` 11 | 含 `dept_id` 映射 |

## 5. §5 原越界项（已随第 5 项裁决处置）

`page-person.js` 的「同一人第 4 个标签需政法委主管审批」已按 D4 原则降级：

- 拦截逻辑：`if (is4th && !ROLE.can.approve) return false` → **删除**（不再因权限不足拒绝）
- 语义：超过 3 个标签视为「超建议上限」，追加时强制填依据（原有 ≥2 字校验保留），审计记为
  `第 N 个标签（超建议上限 · 部门登记确认，报政法委备案）`
- 提示语：`已追加（超建议上限 · 已报政法委备案）`
- 卡头副标题：`上限 3 个，第 4 个需主管审批` → `建议上限 3 个，超限须部门登记确认并报政法委备案`

`approve` 权限位仍保留，用途收敛为**明文导出审批**（数据安全闸门，与 D4 无关）。
